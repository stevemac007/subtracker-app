## Context

SubTracker currently deploys to Netlify via manual CLI commands (`make deploy` / `make deploy-prod`). The GitHub Actions workflow (`github-flow.yml`) runs CI (lint, test, build) but does not deploy. There is no way to preview a feature branch's build before merging, and production deploys are ad-hoc.

The Netlify site ID is `116aa2ae-1526-477d-bafe-a9d2a3e182fc`. The project builds with `npm run build` and outputs to `dist/`. It's a static SPA that needs a catch-all redirect to `index.html`.

## Goals / Non-Goals

**Goals:**
- Automated preview deploys on every PR so reviewers can test changes live
- Automated production deploy on merge to main
- Deploy URLs posted as PR comments for easy access
- Single source of truth for Netlify build config in the repo (root `netlify.toml`)
- CI must pass before deploy (deploy jobs depend on the existing CI job)

**Non-Goals:**
- Branch-specific environment variables or feature flags
- Multiple Netlify sites (we use one site with branch deploys)
- Removing the manual `make deploy` commands (they remain as fallback)
- Deploy notifications to Slack or other services
- Custom subdomains per branch

## Decisions

### 1. Use `nwtgck/actions-netlify` GitHub Action for deploys

**Rationale:** This is the most popular community action for Netlify deploys from GitHub Actions. It handles both preview and production deploys, automatically comments deploy URLs on PRs, and supports the `--alias` flag for predictable preview URLs. The alternative — using raw `netlify-cli` in a run step — requires more boilerplate and manual PR comment logic.

**Alternative considered:** Official `netlify/actions/cli` — less maintained, fewer features around PR comments.

### 2. Extend existing workflow rather than creating separate workflow files

**Rationale:** The project already has `github-flow.yml` with CI steps. Adding deploy jobs to the same workflow (with `needs: ci` dependency) keeps everything in one place and ensures deploys only happen after CI passes. Separate workflow files would duplicate trigger configuration and make the dependency less explicit.

### 3. Root-level `netlify.toml` for build configuration

**Rationale:** Moving build config into a committed `netlify.toml` at the repo root makes the deploy configuration version-controlled and reviewable. The existing `.netlify/netlify.toml` is auto-generated by the Netlify UI and shouldn't be relied on. The root file will define the build command, publish directory, and SPA redirect rules.

### 4. GitHub Secrets for credentials

**Rationale:** `NETLIFY_AUTH_TOKEN` (personal access token) and `NETLIFY_SITE_ID` are stored as GitHub repository secrets. This is standard practice — secrets are masked in logs and only available to workflows running on the repo.

### 5. Deploy alias based on PR number

**Rationale:** Using `deploy-preview-${{ github.event.number }}` as the alias gives each PR a predictable, stable URL (e.g., `deploy-preview-42--subtracker.netlify.app`). This is better than random deploy IDs because reviewers can bookmark the URL and it updates on each push.

## Risks / Trade-offs

- **[Netlify free tier build minutes]** → CI builds the project, then the deploy action uploads pre-built `dist/`. Netlify doesn't re-build, so no build minutes are consumed on Netlify's side.
- **[Secret exposure on fork PRs]** → GitHub Actions secrets are not available to workflows triggered by PRs from forks. Deploy previews will only work for PRs from branches within the same repo. This is acceptable for a small team project.
- **[Action version pinning]** → Pin `nwtgck/actions-netlify` to a specific major version tag (e.g., `v3`) to avoid breaking changes while still getting patches.
- **[Stale preview deploys]** → Old preview deploys remain on Netlify after PR merge. Netlify auto-cleans these eventually, and they don't count against bandwidth unless accessed.
